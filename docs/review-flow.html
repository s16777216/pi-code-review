審查與討論自動 resolve 流程

由上而下是執行順序，箭頭是依賴：箭頭起點的產物，是終點的輸入。這是設計中的流程，不是目前的實作。

  • judge agent 與 review agent 在同一高度，表示兩者互不依賴：judge agent 只讀討論、diff 與檔案內容。
  • 4. verify agent 同時接受 finding verifier（3.）的 finding 與 judge agent（2.）的宣告，由它判斷最終輸出的 open issue 與 resolved issue。它負責 finding 與舊討論的對應，可以讀人的回覆，並單獨決定是否 resolve，沒有程式端的確定性把關（錨點、證據行）。
  • 下方的表格與「失敗時的處理」描述的是目前的實作，還沒有改成這個流程。

各區塊說明

區塊讀取工作
1. review agent ×3（並行）diff。與討論無關找新問題，產生 finding
2. judge agent（逐檔一次）現有討論、diff、檔案內容。不看任何 finding判斷本工具開的未解決討論：fixed / not_fixed / uncertain，fixed 附證據行
程式碼：移除不在 MR diff 內的 finding1. 合併後的 finding、MR 的 diff不用模型。丟掉檔案不在變更內、行號不在 diff 內，或 diff 被省略的 finding，並寫一行 warn
3. finding verifier上一步留下的 finding整理：同一問題被重複報告時只留一個。驗證：逐檔複核，刪掉被判 rejected 的
4. verify agent現有討論（含人的回覆）、diff、檔案內容；3. 的 finding；2. 的宣告對每個 finding 判斷：新問題，或重複了開著的討論（丟掉），或關聯到已 resolve 的討論（回覆並重開），或人已說明是刻意設計（丟掉）。對每個 2. 的宣告判斷是否 resolve。輸出 open issue 與 resolved issue
輸出4. 的 open issue 與 resolved issuefindings.json（finding、resolved、warnings）→ publish

失敗時的處理

  • judge agent（2.）某個檔案的模型呼叫失敗，或第一次請求超過 context window 的一半：該檔案不 resolve，只寫 warn log，不讓審查失敗，也不新增 warning 代碼。
  • 證據行無效時，程式端丟棄該宣告並寫 warn log（evidence_not_valid，附 problem 欄位）；沒有證據行且錨點還在，原因是 anchor_still_present。
  • 證據行只能證明該行存在，不能證明修正有效。尚未實作的想法：讓 verifier 複查 judge 判為 fixed 的討論。
