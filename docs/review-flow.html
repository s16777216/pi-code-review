審查與討論自動 resolve 流程

由上而下是執行順序，箭頭是依賴：箭頭起點的產物，是終點的輸入。這是目前實作的流程。

  • judge agent 與 review agent 在同一高度，表示兩者互不依賴：judge agent 只讀討論、diff 與檔案內容。
  • 5. verify agent 同時接受 finding verifier（4.）的 finding 與 judge agent（2.）的宣告，由它判斷最終輸出的 open issue 與 resolved issue。它負責 finding 與舊討論的對應，可以讀人的回覆，並單獨決定是否 resolve，沒有程式端的確定性把關。
  • 3. 整理與 4. 驗證是兩個獨立的步驟：整理只比較 finding 的文字，驗證才讀程式碼。

各區塊說明

區塊讀取工作
1. review agent ×3（並行）diff。與討論無關找新問題，產生 finding
2. judge agent（逐檔一次）現有討論、diff、檔案內容。不看任何 finding判斷本工具開的未解決討論：fixed / not_fixed / uncertain
程式碼：移除不在 MR diff 內的 finding1. 合併後的 finding、MR 的 diff不用模型。丟掉檔案不在變更內、行號不在 diff 內，或 diff 被省略的 finding，並寫一行 warn
3. 整理（deduplication）上一步留下的 finding 的檔案、行號、嚴重度與摘要。一次模型呼叫，只在某檔案有 2 個以上 finding 時才呼叫同一問題被重複報告時只留一個（留嚴重度最高的）
4. finding verifier3. 留下的 finding，逐檔處理複核每個 finding，刪掉被判 rejected 的，並給出嚴重度
5. verify agent現有討論（含人的回覆）、diff、檔案內容；4. 的 finding；2. 的宣告對每個 finding 判斷：新問題，或重複了開著的討論（丟掉），或關聯到已 resolve 的討論（回覆並重開），或人已說明是刻意設計（丟掉）。對每個 2. 的宣告判斷是否 resolve。輸出 open issue 與 resolved issue
輸出5. 的 open issue 與 resolved issuefindings.json（finding、resolved、warnings）→ publish

失敗時的處理

  • judge agent（2.）某個檔案的模型呼叫失敗，或第一次請求超過 context window 的一半：該檔案不 resolve，只寫 warn log，不讓審查失敗，也不新增 warning 代碼。
  • 整理（3.）的模型呼叫失敗，或回傳的分組無效：保留所有 finding，寫 warn log，並記錄 warning deduplication_failed，不讓審查失敗。
  • finding verifier（4.）某個檔案的模型呼叫失敗，或第一次請求超過 context window 的一半：保留該檔案的 finding，寫 warn log，並記錄 warning verification_failed 或 verification_skipped，不讓審查失敗。
  • verify agent（5.）某個檔案的模型呼叫失敗，或第一次請求超過 context window 的一半：該檔案的 finding 維持原樣、不 resolve，只寫 warn log，不讓審查失敗，也不新增 warning 代碼。
