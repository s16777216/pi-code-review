目前實作：由 judge agent 判斷本工具開的未解決討論是否已修好，程式端再檢查程式碼。

合併三個輸出；檢查 relatesTo 與 diff 行；為每個 finding 算錨點

② 去重 現有

同一問題被多個 agent 重複報告時，只留一個（1 次模型呼叫）

③ verifier：第一次 現有

  • 逐檔複核 finding：confirmed / rejected / uncertain，並重評嚴重度
  • 只有 rejected 會被刪掉
驗證後剩下的 finding

④ 選出要判斷的討論 現有

本工具開的、未 resolve、有錨點、沒有剩下的 finding 連結。
沒選到任何討論 → 不呼叫模型，直接結束這一段

⑤ judge agent（逐檔一次）

  • 讀：完整筆記（含人的回覆）＋現行程式碼
  • 輸出：fixed / not_fixed / uncertain，附理由；fixed 另附一行證據行
not_fixed、uncertain 到此為止，不 resolve
只有 fixed 繼續

⑥ 程式端檢查 放行條件

  • 討論存在、本工具開的、未 resolve、有錨點
  • 沒有 finding 連結；檔案可讀（已刪除的檔案可略過讀取）
  • 錨點已消失，或 證據行有效：是現行檔案的整行（比對前去除前後空白、合併連續空白、去掉行尾的 ; ,）、單行、至少 8 字元，且不是被指到的那一行
通過 → resolved

輸出

findings.json（finding、resolved、warnings）→ publish 發討論，並對 resolved 的討論回覆後呼叫 GitLab resolve

失敗時的處理

  • ⑤ 某個檔案的模型呼叫失敗，或第一次請求超過 context window 的一半：該檔案不 resolve，只寫 warn log，不讓審查失敗，也不新增 warning 代碼。
  • 證據行無效時，程式端丟棄該宣告並寫 warn log（evidence_not_valid，附 problem 欄位）；沒有證據行且錨點還在，原因是 anchor_still_present。
  • 證據行只能證明該行存在，不能證明修正有效。尚未實作的想法：讓 verifier 複查 judge 判為 fixed 的討論。
